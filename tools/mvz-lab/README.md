# mvz-lab · 音频可视化测量台

用来回答一个本来只能靠嘴争的问题：**这段可视化到底有没有跟着音乐动，动得对不对。**

不产出截图，产出数字。所有结论都能被第三方重跑推翻。

## 四条通道

都挂在 `MusicVisualizer.astro` 上，默认全关，生产路径上每个判断都是常量 false。

| 参数 | 作用 |
|---|---|
| `?seed=N` | 固定随机源（mulberry32）。涟漪落点、流星轨迹全部可复现。 |
| `?fixed=1` | 时钟固定 1/60 秒/帧。测量以帧为单位，免疫 rAF 抖动与机器快慢；同时禁用自适应换档（换档会重建实例缓冲）。 |
| `?stim=NAME` | 用已知的注入信号替代分析器输出。输入已知，输出才可测。 |
| `?rec=1` | 逐帧记录。默认不分配任何缓冲。 |
| `?live=1` | 保留 `mvz=1` 的自动开层，但频谱走真实分析器。整条真实链路。 |
| `?q=0..3` | 强制画质档（超/高/中/低）。一档同时改网格密度、渲染倍率、像素预算、辉光降采样、镜像反射——只改网格是假自适应。 |
| `?field=0` | 关掉方位声场，回到纯地形基线。改空间场参数时的对照组。 |

`?rm=0` 覆盖 `prefers-reduced-motion`（headless 默认报 reduce，不覆盖的话每张图都跑在降级分支上）。

## 刺激场景

输入是「频段值随时间的已知函数」，铺平成 256 bin 时乘 `bandTilt`，消费方再除回去，
中间只经过一次恒等变换——被测对象仍是完整下游链路。

| 场景 | 测什么 |
|---|---|
| `silence` | 无信号时是否退化成死板（噪声基线） |
| `impulse` | 单帧满幅冲击：端到端视觉延迟、衰减时间 |
| `step<N>` | 第 N 段从 0 阶跃到 0.7：上升时间、过冲、稳态增益 |
| `sweep<N>` | 第 N 段 0→1 线性扫描（绕过前端）：证明下游单位增益、线性 |
| `bin<N>` | 同上，但送进 `MusicManager.__shapeBin` 的真实整形 |
| `oldbin<N>` | 复刻旧削顶顺序，**只存在于测试页**，用于单变量对照 |
| `flash<hz>` | 方波脉冲，量真实闪烁频率与幅度 |
| `fourfloor` | 128BPM 四踩，端到端反应度 |

`bin` 与 `oldbin` 是这套台子最重要的设计：同一构建、同一输入、相邻两次运行，
**唯一的变量是削顶与乘补偿的先后顺序**。这类对照能把「因果」和「同时发生」分开。

## 记录格式

每帧 25 个数：

```
0 帧号  1 时间  2 平均亮度(相对亮度)  3 帧哈希  4 punch  5 idle  6 energy
7..14 频段原始值 b0..b7     15..22 平滑值 s0..s7
23 亮区 P90    24 逐像素平均变化量
```

亮度取自真实像素：`blitFramebuffer` 把默认帧缓冲降采样到 120×68 再回读。
测光区剔除播放器卡片——它是静态高亮块，会按比例稀释地形那点变化；
封面图还是异步加载的，不剔掉可复现性永远过不了。帧哈希也只算测光区。

三个亮度量的分工，不能混：
- **平均亮度**：被大片背景稀释，适合看整体曝光，不适合看响应。
- **亮区 P90**：眼睛实际看的那部分有多亮。
- **逐帧变化量**：几何驱动的可视化，「动了多少」比「亮了多少」更接近观感；
  它同时也是 WCAG 闪烁判据要的那个量。

## 分析

`analyze.py` 只用标准库。判据写死在代码里，改判据就是改标准：

| 判据 | 阈值 |
|---|---|
| 阶跃 t63 | ≤50 ms 快 / ≤150 中 / 否则慢 |
| 反应度 r | ≥0.6 跟得上 / ≥0.3 弱 / 否则脱节 |
| 闪烁 | 相邻明暗对 ΔL ≥ 0.10（WCAG 2.3.1） |
| 可复现 | 预热 1.5 s 后逐帧哈希相同 |

## 取景与配色核验（三个独立脚本）

不产出「有没有跟着音乐动」的数字，产出「长什么样」的对照帧。都需要 `pnpm build`
后的 `dist`（`beat-peek` / `ref-capture` 各自起一个本地静态服务器 + CDP Chrome）。

| 脚本 | 作用 |
|---|---|
| `ref-capture.mjs` | 给《音域回响》壁纸注 `wallpaperRegisterAudioListener` 等 WE 宿主 API shim，喂 128 BPM 合成频谱，让参照本体在 headless Chrome 里真跑。`preview.gif` 只有空闲段，不能用来比峰顶色。shim 暴露 `__beat.phase/peaks`，**在跨拍后 1 帧截图**，`--shots` 多帧取样 + `states.json`；`--secs` 是热身秒数。 |
| `beat-peek.mjs` | **在拍点峰值截图**，而不是场景收尾帧——四踩收尾帧多半落在拍间低谷，峰顶色本来就不该出现。写 `beat-N.png` + `states.json`。`--fixed 1` 透传 1/60 固定步长时钟；每次自动用全新 `--user-data-dir`（复用崩溃过的 profile 会 `Abnormal renderer termination`）。 |
| `colorcheck.py` | 截图 → 亮度分位、亮/暗区均色、色相圆周平均与集中度、色族像素数。纯标准库 + ffmpeg。判据是色相族（暖峰 12–70°、紫族 240–315°），不要用「距 peakColor 的 RGB 距离」——经辉光与软压缩后峰顶是蜜桃色，会双双漏判。`--mask x0,y0,x1,y1` 可整块剔除播放器卡片区做敏感性检验（**两端必须用同一矩形**）。 |

配色结论与测量表见 `FINDINGS.md` 第十一、十二节。关于可复现性，
`--fixed` 固定的是**内部积分步长**，不固定 CDP 截图的落帧：多批次间前两帧
可逐字节一致，第三帧可能落在相邻拍。跨运行比较请取**多帧统计范围**，
不要逐帧比对，也不要据单帧下结论。

参照端在 SwiftShader 下只有 2.5–3.2 fps（降分辨率也无明显改善），
拍点相位只代表**输入信号**，不代表画面响应峰值；因此参照的绝对亮度
只作量级参考，正式对照用比率类量（琥珀面积、色相集中度、暗区均色）。

## 已知限制

- headless + SwiftShader：能跑通渲染与像素回读，但 GPU 计时无意义（软光栅）。
- `?live=1` 在本机未接通（频段恒为 0）。真实音频结论仍空缺。
- 默认 `--grid 64`：动力学不受影响，亮区面积会变，P90 绝对值不能直接搬到生产。
- 一次 full run 约 16 分钟，期间**不要重建 dist**——会让后半程跑在另一个构建上，
  数据作废（`out/run3` 就是这么废掉的）。
